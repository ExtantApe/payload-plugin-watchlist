Later on 2026-11-11, before the first release, he replaced it with "Curator's yes for new creators": a new creator's videos wait for a curator's yes, and a curator can switch a trusted creator to automatic. `defaults.videosDefault` is `picked`; `rules` is the per-creator "automatic" setting, and a site can still set the default to `rules`. A stored creator with no value counts as `picked` (fail closed), so a site that had the feature built in sets stored values before it switches. Public reads still need a listed creator.

The terms haven't been read yet (design 0001, "Publishers' terms"), so the default stays `keep`; `clear` empties the title, description, thumbnail, duration and playlists of a video gone 30 days, keeping its YouTube ID, the curator's choice and its topic links.
  - **9a:** only titles and descriptions (with the channel's public name) go to the classifier hook. `classifyDescriptionChars` (default 700, 0 for titles only). Without a `classify` hook nothing shows by the rules.
  - **10:** MIT, public at first release, through the audited first push with the leak check in CI. `LICENSE` added, now "Copyright (c) 2026 EXTANT APE".
- 2026-11-11: phase 1 built on fakes (the core: collections, access, RSS and Data API fetching, the unit ledger, the sync, curation, the player). Choices made in the build:
  - The public read checks the creator through the database (`creator.listed`, `creator.doNotFeature`, `creator.videosDefault`), so unlisting, do-not-feature and a mode change take effect at once. Each video also stores its `curation`, re-set in the same transaction when its creator's mode changes.
  - `shown` is recomputed on every write, the sync's included: a choice wins; otherwise only `curation: rules`, `passedRules` and details from the API. Gone videos never show.
  - The run lock, the unit cap, the review claim and the once-a-day digest are each one atomic MongoDB update. MongoDB only, for now.
  - The daily unit cap counts every site together, since one key serves them all. Quota resets are counted in `America/Los_Angeles` (unverified).
  - Notices (`notify`) go out only when `enabled` is exactly `true`, like every other outside effect.
  - A channel link pasted as the handle gives the channel ID with no API call.
  - The sync never writes `doNotFeature`, and skips such a creator before any call.
  - New fields, all optional: creators `doNotFeature`, `doNotFeatureNote`, `channels[].rssSeen` (and `channels[].curation` only at channel level); videos `embeddable`, `madeForKids`, `source`, `channelId`, `curation`, `passedRules`, `unavailableSince`, `claim`.
  - Left for later phases: the review admin view, the Sync now button and endpoints (the site's cron calls `syncDue`), podcasts and shows display and detection, the old "Own filter" move, the page components besides the player, and the adapters beyond `notify`.
- 2026-11-11 (the security read of 5177185): fixed before review continues.
  - **B1:** every field not meant for the public has field-level read access for an admin and the record's own site's curators and editors only (exact `true`). A query guard (`beforeOperation`) refuses a filter, sort or distinct read on those fields for anyone without a role, inside `and` and `or` and through `creator.` on a video, and keeps a curator's or editor's to their own sites. The public fields are listed in the README. Payload answers a withheld array field with `[]`.
  - **S1:** a video and its creator must be on the same site, for every write, the sync's included; the public read also checks the creator's site, and a mode change re-judges only the creator's own site's videos.
  - **S2:** a person's first change of a video's choice takes the claim atomically, in the write's own transaction; after that only that curator, the site's editors and admins can change the choice (409 otherwise). People never write the claim. A claim taken by a write that then fails rolls back with it.
  - **S3, S4:** the package description is the README's one-liner; keywords follow the plugins' shared tag list (base words, `media`, `integrations`, `multi-tenant`, then function words; no family tags).
  - Nits: editors see only their own sites' units (the total and the digests are admin-only); a creator's website takes http and https only; the iframe allows autoplay so a click starts playback; a quota stop seen by a concurrent run is reported as `quota`; the README says site hooks run after the plugin's `shown` computation; `release.yml` and `RELEASING.md` added, with `"private": true` kept until the first-public-push step.
- 2026-11-11, the site's team: `videosDefault` is public because the site's visibility rules read it. A site's own page queries read it and filter on it, so a signed-out visitor can read and filter on it, also through `creator.` on a video. `channels[].playlists` is public too: a site's pages read the old "own filter" names there. `excludeKeywords`, `minMinutes`, `backfillDone`, the per-channel topic settings and `curation` stay hidden with `uploads`, `backfillToken` and `rssSeen`: they're the curators' own rules and the sync's state, and no page reads them (confirmed by the maintainers, 2026-11-11). The schedule (`syncDays`, `syncHour`) and everything else stays staff-only.
- 2026-11-11: phase 2 built on fakes (Sync now, the review queue, the digest's retry, the public pages, the gone-videos sweep). Choices made in the build:
  - **Schema: one field added, and it stores nothing.** `creators.syncNow` is a `ui` field, the name and type the feature's own button had. No stored field, collection or index was added or changed. Sync now's lock is the run lock already there (`syncingSince`); the digest's claims live in `watchlist-usage.digests` as before.
  - **Sync now** is `syncNow(payload, { req, id })` and `POST /api/creators/:id/sync`: an editor of the creator's site or an admin (exact `true`). Signed out is 401, no editor's role 403, and a creator on another site gets the same 404 as one that doesn't exist. It runs `syncCreator` with `full` and `recheck`, so every call reserves units in the same ledger under the same cap, and the same atomic run lock answers a second click with 409.
  - **The review queue** is `reviewQueue(req)` from `/server` (signed out `signIn`, no role `notStaff`, then a read with the person's own access), the `ReviewQueue` component, and an admin view at `/admin/watchlist-review` (`admin.reviewPath`; `admin: false` leaves it out). Decisions go through `POST /api/videos/:id/review`, which is `reviewVideo` and its atomic claim.
  - **`reviewQueueCount(payload, { req, site? })`** replaces `reviewQueueCount(payload, site)`: it counts only the sites the person curates (every site for an admin) and answers 0 for anyone else. The old form counted any site for any caller.
  - **The plugin's routes survive `overrides`**: they're put back first, so an override's route on the same path can't take their place.
  - **The digest:** a failed send gives its once-a-day claim back, so the next run tries again. The daily digest is skipped on a day the "at once" one already went; the "at once" one still goes after the daily one, once. `syncDue` and Sync now send the "at once" digest themselves when videos were added.
  - **Public pages read as a signed-out visitor**, whoever is signed in: the request's person is left out and the collections' read access decides. No public server function overrides access. The site of the request comes from `scope.ofRequest` without the person, so a site whose `ofRequest` depends on the signed-in person must pass the site another way.
  - **Server functions answer plain JSON or `{ error: { code, message } }`**, as the brief asked.
  - **The gone-videos sweep** (`sweepGoneVideos`, the owner's choice 8a) does nothing with `keep`. With `clear` it asks YouTube again before clearing anything (50 videos a unit, reserved first), so nothing is cleared on a stale mark, without a key, with outside calls off, at the cap or after an error. A video that's back is marked back. The sync's own clearing after a re-check (phase 1) is unchanged.
  - **Admin components** are server components from `/rsc` (`ReviewView`, `ReviewNavLink`, `SyncNowField`) with the client parts in `/client`. `@payloadcms/next` is an optional peer, for the admin's page template only; `@payloadcms/ui` isn't used.
  - Left for later: podcasts and shows display and detection, the old "Own filter" move, the "videos about this topic" block as its own component (the grid with `topic` does the job), the site's other three review queues (new on Watch, hidden by type, reviewed) and inline edits of kind and topics, translations beyond the `text` and `labels` props, and the adapters beyond `notify`.
- 2026-11-11 (the security read of f81e50a: approved, with these to do before the first public push):

The parity snapshot of that site's fields and the script that reads them are out of the repo: `test/parity.test.ts` reads a snapshot from the path in `WATCHLIST_PARITY_SNAPSHOT` and is skipped, saying so, without it. Locally they live in the ignored `.secrets/` folder.
  - **Sync now cooldown:** `syncNow.cooldownMinutes`, default 10 (0 turns it off). A creator synced in that time, by a person or the cron, answers 429 with when to try again (`retryAfter` seconds, and a `Retry-After` header on the route). It reads `lastSyncedAt`, so nothing new is stored. Admins wait too. Access is checked first, so someone who may not sync learns nothing from it.
  - **A site's share of the day's units:** `youtube.siteDailyUnitCap`, no default (a site may use the whole cap unless one is set). It's checked in the same atomic update as the cap, for every run of that site: Sync now, the cron and the gone-videos sweep. A site at its share stops with `site-cap`; the cron and the sweep go on with the other sites. No stored field changed: it reads the per-site count the ledger already kept.

  - Two admin labels lost the word "Watch": "On the video pages" and "Own filter (old)".
- 2026-11-27: **Duplicating is off** for `creators`, `videos` and `watchlist-usage`, for everyone, server code included (K891). A new record is made with an ordinary create. Each collection sets `disableDuplicate`, which `overrides` can't change, and a `beforeOperation` hook refuses any create that carries `duplicateFromID`, with one answer for every id. At startup the plugin sets the flag again and puts the hook first and last. The sync only makes ordinary creates, so nothing inside the plugin changes. Leave `disableOnInit` off.
- 2026-11-27: **The sync's and the review's fields aren't set by a person's write,** admins included, on create or update (K891; the list is in the README's Access section). Sent values are dropped without an error, because the admin sends the whole record back on save. YouTube's facts about a video (`unavailable`, `embeddable`, `madeForKids`) are on the list. The text a person may need when adding a video by hand (title, description, publish date, thumbnail, duration, playlists) and a creator's public details (avatar, bio, channel title and ID, show logos) stay writable. Server code writes with no person on the request. Each of the plugin's own writes gets its own copy of the request's context.
- 2026-11-28: **Write data has to be in the shape of the collection's fields** (K891). A create or update on `creators`, `videos` or `watchlist-usage` is refused with a 400 when its data has a key that starts with `$` or contains a dot (json and rich text field contents excepted), or when one list has two rows with the same id. A list field takes a list, `null`, the number `0` or the text `'0'`. The admin sends an empty list as 0, and Payload saves `0` and `'0'` as an empty list. Anything else in a list field is refused the same way. The write is refused whole, with nothing dropped from it. The rule covers server code with no person too, and the plugin's own writes pass it. Writes made straight through the database adapter skip Payload's hooks and aren't checked.
- 2026-11-28: **A channel row moved to a different channel starts its sync over** (K891). The row's sync state describes one channel, so when a person points the row at another one, the next sync looks it up and reads its uploads from the start. State is kept when the resolved channel ID is unchanged, such as a handle swapped for the same channel's link.
