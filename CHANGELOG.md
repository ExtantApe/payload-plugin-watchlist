# Changelog

## 0.2.0 (2026-11-28)

- **Upgrade note: write data must match the collection's fields.** A create or update on `creators`, `videos` or `watchlist-usage` is refused with a 400 when its data has a key that starts with `$` or contains a dot (json and rich text field contents excepted), or when one list has two rows with the same id. A list field takes a list, `null`, the number `0` or the text `'0'`. The admin sends an empty list as 0, and Payload saves `0` and `'0'` as an empty list. Anything else in a list field is refused the same way. The error is "Watchlist couldn’t save this: the data isn’t in the shape of the collection’s fields." This covers every write, including server code with no user and `overrideAccess: true`. If your own code builds write data from outside input, pass field values only. Writes made straight through the database adapter or Mongoose skip Payload's hooks and aren't checked. **A channel row that a person moves to a different channel starts its sync over:** the next sync spends one Data API unit to look it up, then reads its uploads from the start. A handle edit that resolves to the same channel keeps its state. Tested: typecheck, build, the leak check and the full suite twice (391 run, 2 skipped without the parity snapshot) on Payload 3.92.1 with an in-memory MongoDB: the Local API, REST through Payload's request handler, and GraphQL run against the schema Payload builds; the tests in `test/shapeWalk.test.ts` call the check directly. Not tested: the admin in a browser, GraphQL through its HTTP route, the SQL adapters, other Payload versions, or a live site.
- **Upgrade note: a person's write no longer sets the fields that belong to the sync and the review**, on create or update, for every role, admins included. On videos: `claim`, `hiddenReason`, `ruleKey`, `passedRules`, `source`, `curation`, `channelId`, `unavailable`, `unavailableSince`, `embeddable`, `madeForKids` and the topic names. On creators: `lastSyncedAt`, `lastRecheckAt`, `lastFullSyncAt`, `syncingSince` and `syncNote`, and on each channel `uploads`, `backfillToken`, `backfillDone` and `rssSeen`. A sent value is dropped without an error and the stored one stays (a new video starts with `unavailable` off). A "person's write" is any write with a user on the request, so if your own code, an import or a seed script sets one of these while passing a user or a signed-in request, write it with no user. A video a person adds shows only through a person's choice. Records already stored aren't changed or checked. The plugin's own writes use their own copy of the request's context. Writes you make on a request you also pass to a sync or sweep, or use for a creator change that re-judges videos, are treated as yours: the rules above apply to them, and your creator changes call `revalidate`. Tested: typecheck, build, the leak check and the full suite twice (391 run, 2 skipped without the parity snapshot) on Payload 3.92.1 with an in-memory MongoDB, over the Local API and REST through Payload's request handler. Not tested: GraphQL, the admin in a browser, the SQL adapters, other Payload versions, or a live site.
- **Upgrade note: duplicating is off** for `creators`, `videos` and `watchlist-usage`, for everyone, admins and server code included. `payload.duplicate` is refused, and so is `payload.create` with `duplicateFromID` (403, "Watchlist records can’t be duplicated. Make a new one instead."). The REST duplicate route and the GraphQL duplicate mutations are no longer built, and the admin has no Duplicate action for these collections. If your code or your editors duplicated a record, make a new one with an ordinary create that passes the fields you want. An `overrides` entry that sets `disableDuplicate: false` no longer turns it on, and the plugin sets the rule again at startup, in an `onInit` that runs after your config's own and those of plugins listed before Watchlist. A plugin listed after Watchlist can still run code after it, so list any plugin that could turn duplicating on before Watchlist, and don't set `disableOnInit`. Ordinary creates work as before. `@payloadcms/graphql` 3.92.1 is a new dev dependency, for the tests. Tested: typecheck, build, the leak check and the full suite twice (391 run, 2 skipped without the parity snapshot) on Payload 3.92.1 with an in-memory MongoDB: the Local API, REST through Payload's request handler, and GraphQL run against the schema Payload builds. Not tested: GraphQL through its HTTP route, the admin in a browser, the SQL adapters, other Payload versions, or a live site. The four new `scripts/mutate.py` entries for this were each caught, run in a copy; `docs/test-audit.md` says which older entries were rerun.
- Tests for the transaction fix (`test/transactions.test.ts`): the creator and video lookups, the creator list and the two hooks that read inside a write pass `pagination: false`, and every public find is made as a signed-out visitor with access checked. Tested: typecheck and the full suite (289 run, 2 skipped without the parity snapshot); the two tests for the fix failed on the source before it. Not tested: the race itself, which needs a real replica set and luck, and the paged lists inside a transaction.

## 0.1.0 (2026-11-11)

Phases 1 and 2, on fakes. Not on npm; no site uses it.

- `creators`, `videos` and `watchlist-usage`, with the site's slugs and field names, and the plugin's rules kept through `overrides`.
- Access that passes only an exact `true`: the public reads shown videos of listed creators that aren't picked-pending; curators review their site; editors manage it.
- RSS first, then the Data API with a key the site passes in; a daily unit cap, a quota stop and retries after 2 and 8 seconds.
- The per-channel rules, the classifier hook (titles and descriptions only), topic pages, the weekly re-check, the monthly full read and the run lock.
- `syncDue` for the site's cron, `syncCreator`, `reviewVideo` with an atomic claim, `reviewQueueCount` and `sendReviewDigest`.
- `Player`: click to play, youtube-nocookie, a link out when embedding is off.
- Security read fixes: internal fields hidden from the public and refused in filters and sorts; videos and creators on the same site; a curator's claim holds against plain edits; per-site unit ledger; http and https websites only.
- Sync now: `syncNow` and `POST /api/creators/:id/sync` for a site's editors, with a button on each creator, through the same unit ledger, daily cap and run lock.
- The curator's review queue: `reviewQueue`, the `ReviewQueue` component, an admin view with a nav link and count, and `POST /api/videos/:id/review`.
- `reviewQueueCount(payload, { req, site? })` counts only what the person may review. It replaces `reviewQueueCount(payload, site)`.
- The digest retries a failed send on the next run, and the daily one is skipped on a day the "at once" one went. `syncDue` and Sync now send the "at once" digest themselves.
- Public pages: `listCreators`, `getCreator`, `listVideos` and `getVideo` from `/server`, and `CreatorListPage`, `CreatorPage`, `VideosPage`, `VideoGrid` and `VideoPage` from `/pages`, with the site's shell, empty state and topic filter as slots.
- `sweepGoneVideos` for the site's cron: with `goneVideos.mode: 'clear'`, clears the stored details of videos YouTube still reports gone, inside the unit cap.
- A creator's `videosDefault` and each channel's `playlists` are publicly readable and filterable, because the site's pages read them.
- The plugin's routes stay through `overrides`.
- Sync now rests a creator for `syncNow.cooldownMinutes` (10) after any sync and answers 429 with when to try again. `youtube.siteDailyUnitCap` gives each site its own share of the day's units.
- The review route answers a signed-out visitor 401.
- The parity test reads its snapshot from `WATCHLIST_PARITY_SNAPSHOT` and is skipped without it.
